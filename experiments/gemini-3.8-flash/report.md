# 実験レポート: gemini-3.8-flash

**実施日**: 2026-09-03
**実験者**: Claude Code（コマンダー実行、ユーザー GO/NO-GO 判断あり）
**計画**: [plan.md](plan.md)（PR #142 でマージ）
**比較対象**:

- B4 (`gemini-3-flash-preview`, Temp 1.0 / TopP 0.95 / Think LOW) — 現行精度枠のチャンピオン（depression Recall 96.1% / ~$1.70 per 1K）
- `gemini-3.7-flash`（直前世代、最良 E3 MEDIUM: Recall 91.1% / $3.27 per 1K、却下）
- 現行デフォルト `gemini-3.1-flash-lite` (GA C1, Recall 93.6% / ~$0.30 per 1K)

## 1. 結論（先に書く）

**却下（現行維持）。** depression Recall は **88.93%**（threshold 0.5）で、判定表の「< 0.93 → 現行維持」に該当する。計画の段階実行ルール（フル F1 で Recall < 0.93 なら F2 は実行しない）に従い、**F2 (`thinking_level: medium`) は実行していない**。

ただし事前予想（plan.md「(b) thinking トークンが増えコストは 3.7 世代以上になる」）は**外れた**。3.8 は 3.7 LOW に対し思考トークンが約 1/5 で、**$0.98/1K件と B4 より安い**（0.58倍）。安くはなったが、感度は 4 世代連続で 95% に届かず、しかも 3.7 よりさらに下がっている。

**Phase 1 実コスト合計: 約 $2.01**（Phase 0 プローブ 6件 ≒ $0 + F1 smoke $0.047 + F1 フル残り $1.913。フル集計値 $1.9599 は smoke の 50 件を再開で取り込んだ全 1,993 件分）。

## 2. Phase 0 プローブ結果（実測、各1リクエスト）

`gemini-3.7-flash` の E2 事故（非対応パラメータに気づかず smoke 50 件を潰し、無効な数値を出した）の再発防止として、フル実行前に実測した。生ログ: `results/phase0_2026-09-03T02-16-23.json`。

| # | 確認事項 | 結果 | 判定 |
|---|---|---|---|
| P0-1 | `models.list` の存在と対応メソッド | 存在する。`supportedGenerationMethods` = `generateContent` / `countTokens` / `createCachedContent` / `batchGenerateContent`。**`streamGenerateContent` は列挙されていない** | 要注意（後述 2.1） |
| P0-2 | トークン上限 | `inputTokenLimit=1,048,576` / `outputTokenLimit=65,536`（公称通り） | OK |
| P0-3 | `thinking_level: low` / `medium` | 両方 HTTP 200 | OK |
| P0-4 | `temperature` / `topP` を**送った**場合 | **HTTP 200**（400 にはならない） | OK（2.2） |
| P0-5 | `temperature` / `topP` を**送らない**場合の `usageMetadata` | HTTP 200 / finishReason=STOP。ただし `thoughtsTokenCount` が**欠落** | 形式 NG・実害なし（2.3） |
| P0-6 | `responseMimeType: application/json` + `responseSchema` | スキーマ通りにパース成功 | OK |

### 2.1 `streamGenerateContent` は models.list に列挙されないが実際には 200 を返す

P0-1 の `supportedGenerationMethods` に `streamGenerateContent` が含まれていない。しかし P0-3〜P0-6 のプローブも本実験のランナーも全て `streamGenerateContent` を叩いており、**1,993 件すべてが HTTP 200・フォールバック 0 件**で完了した。つまり「列挙されていないが動く」状態。

含意: 3.8 を将来 UI に載せる場合、`models.list` の `supportedGenerationMethods` を根拠にした対応判定ロジックを書くと 3.8 を誤って除外する。判定は実呼び出しで行うこと。また Google 側がいつ非対応にするかは保証されない。

### 2.2 `temperature` / `topP` を送っても 400 にならない

plan.md が「400 だった場合は『3.8 を UI に載せるには省略経路が必須』という別 Issue になる」としていた懸念は、**実測で消えた**。200 が返る（無視されるのか反映されるのかは本実験では区別していない）。PR #142 で入れた `temperature` optional 化は、公式が非推奨としている以上そのまま有用だが、**3.8 のために必須ではなかった**。

### 2.3 P0-5 の NG は「思考トークンが 0 だったから欠落した」だけ

プローブのプロンプトが `Reply with a single word: OK.` と些細すぎて thinking が発生せず、`thoughtsTokenCount` フィールドごと省略された。実スクリーニングでは smoke の 50 件で `thoughts=711`、フル 1,993 件で `thoughts=38,368` が取得できており、**コスト試算方法の見直しは不要**。

## 4. 分析

### 4.1 Recall は 4 世代連続で 95% に届かず、しかも過去最低

| モデル | 最良条件の Recall | Precision |
|---|---|---|
| B4 (`gemini-3-flash-preview`) | **96.1%** | 53.4% |
| `gemini-3.5-flash` | 93.2% | 54.6% |
| `gemini-3.6-flash` | 94.6% | 49.6% |
| `gemini-3.7-flash` | 91.1% | 65.6% |
| **`gemini-3.8-flash` (F1)** | **88.9%** | **72.2%** |

B4 に -7.2pp、3.7 最良に -2.1pp、現行デフォルト GA C1 にも -4.7pp。**RQ1 の答えは No**。

### 4.2 「Recall↓・Precision↑」の傾向は継続、むしろ最も強い（RQ3）

3.8 は Precision 72.2%（世代最高）・Specificity 94.4%（世代最高）で、判断が**明確に除外方向へ寄っている**。FP は B4 の 235 件に対し 96 件と 41%、その代わり FN が 11 件 → 31 件と約 3 倍。TiAb スクリーニングでは FN が実害（見落とし）なので、この寄り方は用途と逆行する。

「難タスクでは検証を挟む」という 3.8 の設計目標（自律エージェント向け）は、**曖昧なら含める**という系統的レビューの原則とは方向が違う。プロンプトは "If you are unsure ... you MUST include the study." と明示しているにもかかわらず、世代が上がるほど従わなくなっている。

### 4.3 コストは事前予想と逆に下がった（RQ2）

$0.983/1K件は **B4 の 0.58 倍、3.7 LOW の 0.79 倍、3.7 最良 (MEDIUM) の 0.30 倍**。単価は 3.7 と同額なので、差は消費トークン量の差である。3.7 LOW の thoughts 192,505 に対し 3.8 LOW は 38,368 と**約 1/5**。「トークン消費が増える設計」という公式の記述は、少なくとも TiAb のような短い分類タスク＋`thinking_level: low` では当てはまらなかった。

2027-01-01 の価格改定後は $1.97/1K件（B4 比 1.16倍）。それでも予算上は問題にならない水準だが、**Recall が基準未達なので採否には影響しない**。

処理は 41ms/件（concurrency 60）で 1,943 件を 79.5 秒。速度も問題ない。

### 4.4 F2 (medium) を実行しなかった理由

計画の打ち切り規則そのまま: フル F1 の Recall が 0.93 未満のため。根拠は 3.7 世代の実測で、LOW → MEDIUM の Recall 改善が **+0.36pp**（90.71% → 91.07%）に対しコストが **2.6 倍**だったこと。3.8 で同じ改善幅を仮定すると 88.93% → 約 89.3% で、目標 95% には 5.7pp 足りない。$4〜6 を追加しても結論は変わらない。

## 5. threshold スイープ（API 追加費用ゼロ）

保存済み JSONL の `include_probability` から再計算。全文は [threshold_sweep.md](threshold_sweep.md)。

確率分布: <0.1 = 1,499 件 / 0.1–0.5 = 149 件 / 0.5–0.9 = 99 件 / ≥0.9 = 246 件

| threshold | Recall | Specificity | Precision | Fβ(7) | TP | FP | TN | FN |
|---|---|---|---|---|---|---|---|---|
| 0.05 | **97.5%** ✅ | 75.0% | 38.9% | 94.6% | 273 | 429 | 1,284 | 7 |
| 0.10 | 94.3% | 86.6% | 53.4% | 92.9% | 264 | 230 | 1,483 | 16 |
| 0.15 | 92.9% | 89.4% | 59.0% | 91.8% | 260 | 181 | 1,532 | 20 |
| 0.20 | 92.9% | 89.5% | 59.1% | 91.8% | 260 | 180 | 1,533 | 20 |
| 0.30 | 92.1% | 91.6% | 64.2% | 91.3% | 258 | 144 | 1,569 | 22 |
| 0.40 | 90.7% | 92.6% | 66.7% | 90.1% | 254 | 127 | 1,586 | 26 |
| 0.50 | 88.9% | 94.4% | 72.2% | 88.5% | 249 | 96 | 1,617 | 31 |

**閾値を下げれば Recall 95% には届く（0.05 で 97.5%）が、B4 に対する優位は生まれない**:

- threshold 0.05: Recall 97.5% / Precision **38.9%**。B4（96.1% / 53.4%）に対し Recall +1.4pp と引き換えに Precision -14.5pp。FP は 429 件で B4 の 235 件の 1.8 倍
- threshold 0.10: Recall 94.3% / Precision 53.4%。**Precision は B4 と同値なのに Recall が 1.8pp 低い**（B4 に明確に劣後）

すなわち 3.8 の確率出力は、同 Recall 帯で B4 より Precision が低いか同等どまり。`gpt-5.6` のスイープで得た結論（閾値を下げれば Recall には届くが同 Recall 帯の B4 に Precision で劣る）と同型である。

閾値を下げる運用が意味を持つのは「コストが極端に安い」場合だが、3.8 の $0.98/1K件は現行デフォルト GA C1 の ~$0.30/1K件より 3 倍高い。GA C1 は threshold 0.5 のまま Recall 93.6% / Precision 61.6% を出しており、**低閾値運用の候補としても 3.8 を選ぶ理由がない**。

| フォールバック率 | 0.0% | 0% | ○ |

判定表の該当行は **「Recall < 0.93 → 現行維持（却下）」**。`AVAILABLE_MODELS` への追加は行わない。

## 7. 本実験の留保

- **サンプリング条件が過去世代と揃っていない。** 本実験のみ `temperature` / `topP` を送っていない（公式が非推奨・削除としたため。plan.md のユーザー決定）。過去世代は Temp 1.0 / TopP 0.95。Recall 差 -2.1pp（対 3.7）の一部がこの条件差に由来する可能性は排除できない。ただし P0-4 で「送っても 200 が返る」ことは確認済みなので、条件を揃えた追試は技術的には可能である（本実験では実施していない）
- **F2 (medium) 未実行**のため、3.8 の thinking_level 上限側の挙動は未測定。4.4 の推定は 3.7 世代の外挿に基づく
- **1 データセット（depression）のみ**。過去世代と同じ足切り運用（depression で基準未達なら他データセットに進まない）に従った
