# gemini-decision-1 の並列数の実測（Tier 3）

2026-11-12 実測。Gemini Decisions API の `gemini-decision-1` を本人の Tier 3 キーで、並列 8〜256 で呼んだ。
目的は、このモデルをアプリのプロバイダとして足すときの tier 別バッチ設定（`src/lib/types.ts` の `BATCH_PROFILE_OVERRIDES`）の値を決めること。精度は扱わない（`experiments/gemini-decision-1/` の担当）。

## 結論

- **Tier 3 で効く上限は TPM（毎分1,000万入力トークン）で、RPM（毎分1万5,000件）より先に当たる。** 1件の入力は指示文込みで平均約720トークン（cq1、基準1行の screeningPrompt）なので、TPM は約1万3,800件/分（約230件/秒）に相当する。
- サーバ側に並列の頭打ちは見えなかった。並列128で約360件/秒、256で約600件/秒まで出た。どちらも30〜40秒でTPMを使い切り、429 で20〜47秒止まってから再開した。止まる間を含めた平均は並列128で218件/秒、256で348件/秒。
- 429 の本文には `status`・`RetryInfo`・`QuotaFailure` が無く、待ち時間は `message` の文面（`Please retry in 45s`）にしか書かれていない。アプリの `src/lib/gemini-api.ts` は RetryInfo が無いとき文面から秒数を読むので、その処理をそのまま使える。
- 測定全体で記録は47,403件、要求は48,291回（差の888回は429による再試行）。結果はすべて成功で、空・失敗・不明は0件。429以外のエラー（5xx・400・その他の4xx・タイムアウト・通信エラー・不正な本文）も0件。費用は入力34,786,765トークンで **$3.48**（$0.10 / 100万トークン）。

## 推奨値（プロバイダを足すときに使う値）

決め方: 1スロットは1件に約0.33〜0.40秒かかる（p50）。上限の約7割までに収まる並列数を選び、待機（`delayBetweenRequests`。各スロットの最低滞在時間）を300ms以上にして、応答が速くなっても上限を超えないようにする。利用者の基準文が長いと1件のトークンが増えるので、TPM は**1件1,000トークン**で見積もった。保存単位は TypeSafe と同じく並列数に揃える。

| tier | 公式の上限（RPM / TPM / RPD） | 1,000トークン/件での TPM 相当 | 推奨 concurrency | 推奨 delayBetweenRequests | 送信速度の上限（並列 ÷ 待機） | 推奨 saveBatchSize | 根拠 |
|---|---|---|---|---|---|---|---|
| free | 200 / 50,000 / 10,000 | 50件/分 | 1 | 1,500 ms | 40件/分 | 5 | 公式表から算出（未実測） |
| tier1 | 1,500 / 1,000,000 / 50,000 | 1,000件/分 | 4 | 350 ms | 686件/分 | 4 | 公式表と実測の遅延から算出（未実測） |
| tier2 | 5,000 / 4,000,000 / 無制限 | 4,000件/分 | 16 | 300 ms | 3,200件/分 | 16 | 公式表と実測の遅延から算出。並列16の実測は44件/秒（2,640件/分） |
| tier3 | 15,000 / 10,000,000 / 無制限 | 10,000件/分 | 40 | 300 ms | 8,000件/分 | 40 | 実測。並列32で93件/秒、64で170件/秒、429は0件 |

- tier3 の 40 は、1件720トークンなら毎分約500万〜580万トークン（TPMの5〜6割）、1,000トークンでも最大800万（8割）に収まる。並列64（170件/秒）は720トークンで毎分約740万トークンになり、30秒の段では429が出なかったが、基準文が長いプロジェクトや同じキーを使う他の処理があるとTPMに当たる。TPMに当たると30〜45秒止まるので、並列を上げて得る時間より止まる時間が大きい。
- 並列40は実測していない。並列32と64の実測から見込むと約115〜130件/秒で、depression と cq1〜cq5 の18,638件なら約3分。
- tier1 は、本走の並列8（約25件/秒＝1,500件/分）が RPM 1,500件/分と TPM の両方を超えるので、並列8より下げる必要がある。RPD 5万件があるので、5万件を超える文献集合は1日で終わらない。
- 支出の上限（10分あたり Tier 1 $10、Tier 2・3 $200）は、1件約$0.00007なので実用上は当たらない。
- Gemini Decision は Batch API に対応していない（公式表の注記）。

TypeSafe（全 tier で並列64・待機0）と違う値にしたのは、TypeSafe には tier の上限が無いのに対し、Gemini Decision は tier ごとの TPM が効くため。

- 上の表には、別に疎通用の3件（stage `smoke`、$0.0002）がある。

### 429 の中身

- 並列128で370回、256で518回。すべて同じ形で、`error.status` 無し、`details` 無し、`message` が `Rate limit exceeded for model gemini-decision-1 (limit: 10000000 input tokens per minute on Tier 3). Please retry in 45s or upgrade your tier at https://ai.dev/rate-limit.`
- 文面の待ち時間は、並列128で34〜47秒、256で19〜33秒。RPM の429は出ていない。
- 並列256は、429が出る前の30秒で約1,157万トークン（上限の1,000万を超える）を通した。上限の判定は即時ではなく、数秒遅れて効く。

### 時間の推移

`timeline.py` の出力（[timeline.md](timeline.md)）。10秒ごとの完了件数。429 の列は、その10秒に完了した記録が受けた429の回数で、429 が起きた時刻ではない（試行ごとの時刻は記録していない）。

並列128: 0〜40秒は300〜370件/秒、40〜50秒で減速し、50〜70秒は完了0件（全スロットが待機）、70秒から再開。
並列256: 0〜30秒は430〜600件/秒、30〜50秒はほぼ0件、50〜60秒で360件/秒に戻った。

## 段の分け方

- 並列 8・16・32・64・128・256 を、この順に段の間を65秒あけて流した（前の段の要求が次の段の1分の窓に入らないようにするため）。
- 上限に当てるには1分を超えて流し続ける必要があるので、128と256は各2万件前後にした。
- 本走（並列8、`gd-full.log`）が12:18:56に終わったのを確かめてから、12:21〜12:31に流した。同じキーで他の処理は動いていない。
- 入力は `scripts/asreview-baseline/datasets/cq1_labeled.json` の5,628件を seq 順に繰り返した。指示文は `experiments/gemini-decision-1/config.json` と同じ screeningPrompt と cq1 の基準。

## 流し直し方

```bash
node experiments/gemini-decision-1-concurrency/bench.mjs --concurrency 3 --count 3 --stage smoke
bash experiments/gemini-decision-1-concurrency/run-stages.sh
node experiments/gemini-decision-1-concurrency/bench.mjs --summarize > experiments/gemini-decision-1-concurrency/summary.md
PYTHONUTF8=1 python experiments/gemini-decision-1-concurrency/timeline.py c128 c256 > experiments/gemini-decision-1-concurrency/timeline.md
```

- API キーはリポジトリ直下（worktree なら本体のチェックアウト）の `.env` の `GEMINI_API_KEY` を、スクリプトの中だけで読む。
- 1件ごとに `results/<stage>.jsonl` へ追記する。同じコマンドで流し直すと、記録済みの seq を飛ばして続きから送る。段を変えるなら `STAGES="64:5000 128:18000"` のように渡す。
- `--fake` は API に送らない模擬（`FAKE_RPM` で模擬の上限を下げると429の経路を試せる）。
- 1件ごとの台帳 `results/*.jsonl`（約16MB）は git に入れず、`G:\マイドライブ\coding-data\tiab-review-plugin\gemini-decision-1-concurrency\` に zip で置いた。
