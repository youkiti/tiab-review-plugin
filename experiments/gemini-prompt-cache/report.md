# 実験レポート: Gemini implicit caching によるスクリーニングコスト削減（否定的結果）

**実施日**: 2026-09-01
**実験者**: Claude Code（バッチ実験は実行せず、事前計測のみ実施）

## 1. 要約

tiab スクリーニングのユースケースでは、Gemini の implicit prompt caching は**原理的にコスト削減として成立しない**。本実験は当初の計画（`plan.md`。本レポートに置き換えて撤去。PR #137 の初回コミット `ecaf27b` に残っている）に沿ってバッチ実行を回す前提だったが、実行前の事前計測で結論が出たため、**実際のバッチ実験（depression データセットでの4条件比較）は実行していない**。以下は事前計測の実測データと、それに基づく損益分岐の導出、および結論である。

## 2. 当初の仮説と、それが誤りだった点

PR #137 は次の仮説で設計されていた:

- Gemini Flash 系の implicit caching 最小トークン数は約1,024（公表値の下限）
- 現行の depression 用 screeningPrompt（P0、約109トークン）はこの閾値未満でヒットしない
- 閾値を超えるよう設計した長いプロンプト（P1、約1,978トークン）ならヒットし、コスト削減が観測できる

実測の結果、**この前提は誤りだった**:

- `gemini-3.1-flash-lite` の実測閾値は約1,024ではなく**約6,400トークン**
- P1（1,978トークン）は閾値の遥か下であり、そのままバッチ実験を回せば4条件すべてでヒット率0%になり、「implicit caching は使えない」という**偽陰性**の結論を生む設計になっていた
- そもそも後述の損益分岐の式により、**プロンプトを水増しして閾値に届かせる方向自体が原理的に損**であることが分かった

## 3. 実測データ

### 3.1 トークン数（`countTokens` API, `gemini-3.1-flash-lite`）

| 対象 | 文字数 | トークン数 |
|---|---|---|
| 現行 depression 用 screeningPrompt（P0 相当） | 564 | **109** |
| PR #137 の P1 プロンプト | 9,882 | **1,978** |
| 文献ブロック（タイトル＋抄録＋出力指示）30件平均 | — | **387.9**（最小 132 / 最大 853） |

合計 ≈ 497 トークン/件。[`experiments/gemini-3.7-flash/report.md`](../gemini-3.7-flash/report.md) の実測値 979,459 ÷ 1,993 = 491.4 トークン/件 と整合する。

### 3.2 プレフィックス長を振ったときのキャッシュヒット

条件: `gemini-3.1-flash-lite` / temperature 0 / `responseSchema` あり / 逐次送信 / 各長さで**同一プレフィックス**を3件

| 目標プレフィックス長 | promptTokenCount | cachedContentTokenCount |
|---|---|---|
| 3,000 | 3,584 / 3,325 / 3,256 | 0 / 0 / 0 |
| 3,600 | 4,233 / 3,974 / 3,905 | 0 / 0 / 0 |
| 4,000 | 4,637 / 4,378 / 4,309 | 0 / 0 / 0 |
| 4,300 | 4,939 / 4,680 / 4,611 | 0 / 0 / 0 |
| 5,000 | 5,696 / 5,437 / 5,368 | 0 / 0 / 0 |
| 6,000 | 6,715 / 6,456 / 6,387 | 3,964 / 3,959 / 3,957 |
| 8,000 | 8,801 / 8,542 / 8,473 | 3,994 / 3,991 / 3,990 |

各ターゲットのプレフィックスは共通の `GUIDANCE_PARAGRAPH` を繰り返して先頭から切り詰めて生成しているため、短いターゲットのプレフィックスは長いターゲットのプレフィックスの先頭部分と一致する。上表は目標長を昇順（3,000→8,000）に流しているため、6,000 と 8,000 の行は他の行と異なり**1件目（#1）から既にキャッシュがヒットしている**（3,964 / 3,994）。これは3.3節の P1×5連結の実験（プレフィックスが新規だったため #1 が cold miss で #2 以降がヒット）との違いの理由であり、閾値の結論そのものは揺らがない（5,696トークンでは同一プレフィックスを3回投げてもヒットしないという事実が独立して示している）。

→ 実測から言えるのは、**ヒットしなかった最大の promptTokenCount は 5,696**、**ヒットした最小の promptTokenCount は 6,387** であり、閾値はこの区間 **5,696 < 閾値 ≤ 6,387** にある（約6,400トークンを超えてからヒットが現れる）。この区間は 3.5 節の再現によりさらに狭まる（後述）。

### 3.3 補助的な確認

| 確認内容 | 結果 |
|---|---|
| P0 そのまま（前置き109トークン）を4件逐次 | prompt 265〜593、`cachedContentTokenCount` はレスポンスに現れず（=0） |
| P1 そのまま（前置き1,978トークン）を8件逐次 | prompt 2,134〜2,610、同じく0 |
| **完全に同一のリクエスト**を3回（prompt 2,450） | 3回とも0。**反復回数の問題ではなく閾値の問題**であることの確認 |
| P1×5連結（前置き約9,500トークン）を4件 | prompt 10,374 / 10,115 / 10,046 / 10,328 → cached **0 / 8,015 / 8,014 / 8,018** |
| 同上・`responseSchema` なしで3件 | prompt 10,374 / 10,115 / 10,046 → cached **0 / 4,083 / 4,083**。schema はキャッシュを阻害しない |
| `gemini-3-flash-preview` で P1×5連結を3件 | prompt 10,374 / 10,115 / 10,046 → cached **0 / 8,021 / 8,020**。精度枠のモデルでも同様に効く |

観察として、**キャッシュされるトークン数は共有プレフィックス全体とは一致せず量子化されている**（8,801トークン投げても 3,994 しか乗らない）。約4,000と約8,015付近に値が集まるためブロック単位の可能性があるが、**本レポートではそこまでは特定していない**。

**注記**: 公表されている "context caching" 単価は explicit caching の文脈で記載されているものであり、implicit caching のヒット分が同一単価で課金されるという前提は**未検証**（confidence: medium）。ただし後述のとおり、この倍率が多少違っても結論は変わらない。

また、PR #137 の `config.json` が仮置きしていた単価（flash-lite $0.10/$0.40、gemini-3-flash-preview $0.30/$2.50）は**すべて誤りだった**。

### 3.5 コミット済みスクリプトによる独立再現

コミット済みの [`measure-cache-threshold.ts`](measure-cache-threshold.ts) を以下のコマンドで実行し、3.2 節の知見を独立に再現した。

```bash
npx ts-node --project experiments/gemini-prompt-cache/tsconfig.json \
  experiments/gemini-prompt-cache/measure-cache-threshold.ts \
  --model gemini-3.1-flash-lite --targets 5000,6000 --repeats 2
```

| 目標プレフィックス長 | promptTokenCount | cachedContentTokenCount |
|---|---|---|
| 5,000 | 5,174 / 4,915 | 0 / 0 |
| 6,000 | 6,111 / 5,852 | **3,951 / 0** |

この再現は 3.2 節とは異なるフィラー文（スクリプトに埋め込まれた `GUIDANCE_PARAGRAPH`）を使っているため、3.2 節の測定系とは独立した確認になる。それでも同じ閾値付近の挙動が再現した。

**最も重要な観察**: 6,000 の行では、**同一のプレフィックスを使っているにもかかわらず #1（promptTokenCount 6,111）はヒットし、#2（promptTokenCount 5,852）はヒットしなかった**。#2 は抄録が短い文献だったため総トークン数が閾値を下回ったと考えられる。これは**キャッシュ参照の可否がプレフィックス長ではなくリクエスト全体のトークン数で決まる**ことを示している。実運用では抄録の長さが文献ごとにばらつくため、閾値付近では**ヒットする文献としない文献が混在する**ことになり、これも「閾値ぎりぎりを狙う設計は不安定」という結論を補強する。

この再現により、3.2 節で示した区間 `5,696 < 閾値 ≤ 6,387` は **`5,852 < 閾値 ≤ 6,111`** に狭まる（ヒットしなかった最大値が 5,852、ヒットした最小値が 6,111）。

## 4. 損益分岐の導出

記号: `C0` = 現行の共有プレフィックスのトークン数、`I` = 文献ブロックのトークン数、`r` = 入力単価、`m` = キャッシュ単価倍率（実測 0.10）

- 現状の入力コスト/件: `(C0 + I) × r`
- プレフィックスを `N` トークンまで伸ばし、**前置き全体がヒットした最良ケース**: `(I + m×N) × r`
- 得になる条件: `I + m×N < C0 + I` → `m×N < C0` → **`N < C0 / m = 10 × C0`**

つまり**キャッシュ割引が10倍である以上、プレフィックスは10倍までしか伸ばせない**。

現行は `C0 = 109` なので上限は **N < 1,090 トークン**。しかし flash-lite の実測閾値は約6,400で、**約6倍足りない**。

さらに、この式は「前置き全体がヒットする」最良ケースを仮定しているが、3.2 節のとおり被覆は部分的（8,801投げて3,994）なので、**その最良ケース自体が成立しない**。

閾値が仮に公称の下限 2,048 だったとしても `10 × 109 = 1,090 < 2,048` で成立しない。したがって**単価倍率や閾値の細かい値に結論は依存しない**。

## 5. 結論と、本番に残したもの

- tiab スクリーニングは「共有プレフィックスが小さく、1件あたりの本文も小さい」ため、キャッシュ割引の対象を作るコストが割引額を上回る。プロンプトを水増しして閾値に届かせる方向は**どう転んでも損**。
- 一方、**別の理由ですでにプレフィックスが閾値を超えているユーザー**（詳細な組入基準や few-shot 事例を書いている場合）には効く。implicit caching は Gemini 2.5 以降で**既定で有効**なので、その層には**すでに自動で効いており、実装すべきものは無い**。
- そのため [`src/lib/gemini-api.ts`](../../src/lib/gemini-api.ts) の `cachedInputTokens` 計測（`UsageMetadata.cachedInputTokens`）だけは残す。長いプロンプトを書くユーザーのコスト表示が正確になり、本番に入れて害が無いため。
- explicit caching（`cachedContents`）は最小トークン数が公式ドキュメントの当該ページに記載されておらず**未調査**。ただし implicit と同等以上の最小値なら同じ理由で成立しない見込み（断定はしない）。
