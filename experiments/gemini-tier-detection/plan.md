# Gemini APIキーの無料/有料 tier 判定 — 実験計画

- 対象 issue: [#88 無料のGemini APIキーが常に「有料」と誤判定される](https://github.com/youkiti/tiab-review-plugin/issues/88)
- 前提 PR: [#87 429適応スロットリング](https://github.com/youkiti/tiab-review-plugin/pull/87)（**未マージ**。本実験の実装フェーズの前提）
- 作成日: 2026-08-15
- 実験ディレクトリ: `experiments/gemini-tier-detection/`

> **【2026-08-15 更新】Phase 0〜2 は実施済み。判定方法は確定した。**
> 結果は [report.md](report.md) を参照。要点:
> - `batches.create` に「requests が空の batch」を送ると、無料キーは `400 FAILED_PRECONDITION`、
>   有料キーは `400 INVALID_ARGUMENT` を返す。**1リクエスト・課金ゼロ・0.1〜0.5秒**で判定可能（16/16 一致）。
> - `models.list` は**集合レベルでも**完全一致（54件）。件数以外でも判定不可と確定。
> - Tier 1/2/3 の自動判定は不可能。手動選択で確定。
> - **issue #88 の案A（429の FreeTier で無料に固定）は採用しない** — 有料 Tier 2/3 でも FreeTier
>   バケットに落ちる既知事象があり、有料ユーザーを無料に固定してしまうため。
>
> 以下の §3〜§5 は実施前の計画をそのまま残してある（Phase 3 以降は未実施）。

## 1. 背景（確定済みの事実。再検証しない）

| # | 事実 | 根拠 |
|---|------|------|
| F1 | `models.list` の**件数**では判定できない。無料キーでも50件返る | 2026-08-14 実測 (issue #88) |
| F2 | 429 の `QuotaFailure.violations[].quotaId` に `...-FreeTier` が明示される | PR #87 実測。`parseGeminiErrorPayload()` で抽出済み |
| F3 | 無料枠の実効上限は `gemini-3.1-flash-lite` で 15 RPM | 2026-08-14 実測 |
| F4 | 現状の既定は危険側に倒れている | [batch.ts:70](../../src/sidepanel/features/llm/batch.ts#L70) が `getManualTier() \|\| 'tier1'`、[types.ts:343](../../src/lib/types.ts#L343) の `ApiTier` はモデル数分岐前提 |
| F5 | UI に「無料」の選択肢が無く、誤判定を是正できない | `#tier-select` は tier1/2/3 のみ |

つまり **「モデル数で判定」だけが壊れている**のではなく、「判定に失敗したときの既定が Tier 1」「手動で戻せない」の3点セットで事故になっている。

## 2. リサーチクエスチョン

| RQ | 問い | 判定基準 |
|----|------|----------|
| **RQ1** | APIキーのみ（OAuth・サービスアカウント無し）で free/paid を確定できる観測量は存在するか | 感度・特異度ともに 6/6 試行で一致 |
| **RQ2** | それは「1リクエスト・課金ゼロ・数秒」で得られるか（キー登録時に同期実行できるか） | §5 の合格基準 |
| **RQ3** | paid 内の Tier 1/2/3 は区別できるか | **仮説: 不可**（quotaId に tier 表記が無い）。反証されなければ手動選択で確定 |
| **RQ4** | 無料枠の RPD（1日あたり上限）の実値と、超過時の quotaId 文字列 | 一括判定の中断メッセージに必要。docs + 日和見的な実測 |
| **RQ5** | 現行 free プロファイル（concurrency 1 / 13,000ms = 実効4.6 RPM）は過剰に保守的か | F3 が正なら 15 RPM まで上げられ、無料ユーザーの処理速度が約3倍になる |

codex に web 調査を委譲する（実行済み: `codex exec --sandbox read-only -c tools.web_search=true`）。調べる範囲・出力形式は `prompt/` 参照。

**打ち切り条件（Phase 1 以降を実施しない条件）:**

- **G0-b**: 「APIキーだけでは原理的に不可能」が公式に明言されている → RQ1/RQ2 は打ち切り、issue #88 の案 A+B（既定 free + 429 で確定 + 手動選択）を実装。実験は RQ4/RQ5 のみに縮小。

## 4. 実験設計

### 4.0 対照（controls）

- **陰性対照 = 無料キー**: `.env` の `GEMINI_API_FREE_KEY`
- **陽性対照 = 有料キー**: `.env` の `GEMINI_API_KEY`
- ⚠️ **実験前にユーザーに確認すること**:
  1. この2キーが**別々の GCP プロジェクト**に属し、有料側だけ課金が有効か（同一プロジェクトの2本目のキーでは対照にならない）
  2. 有料側が現在どの Tier か（RQ3 の答え合わせに必要）
  3. かつて課金を有効にして解除したプロジェクトが無いか（quota が中間状態で残る可能性）

### 4.1 Phase 1 — 課金ゼロ・副作用ゼロの静的シグナル

| ID | プローブ | 観測量 | 期待される差 | コスト |
|----|----------|--------|--------------|--------|
| P1 | `GET /v1beta/models`（全ページ） | モデル名の**集合差分**と各フィールド（`supportedGenerationMethods` / `inputTokenLimit` / preview 系の有無） | F1 は「件数」しか見ていない。**集合が違う可能性は未検証** | 0 |
| P2 | P1 と最小 `generateContent` のレスポンスヘッダ全採取 | `x-goog-*` / `x-ratelimit-*` / その他 | tier 依存ヘッダがあれば最良 | ~0 |
| P3 | `GET /v1beta/cachedContents`, `GET /v1beta/batches`, `GET /v1beta/tunedModels` | HTTP status / エラー body | 有料限定機能なら free で 403 / 429(limit=0) が出る可能性 | 0（list は生成しない） |

Phase 1 で決定的な差が出れば Phase 3（429誘発）は不要になる。**最初に必ずここをやる。**

### 4.2 Phase 2 — 有料限定機能への最小リクエスト

「free キーは即エラー、paid キーは成功して課金はほぼゼロ」という非対称性を探す。**本命は P4。**

| ID | プローブ | 手順 | 中止条件 |
|----|----------|------|----------|
| **P4** | **Batch API** `batches.create` | 1件だけの最小バッチを作成→即 `cancel`/`delete`。free が 429 `...FreeTier`(limit=0) または 403 を返せば **1リクエストで確定** | 作成が成功したのに削除できない場合は即中止 |
| P5 | Context caching `cachedContents.create` | 最小トークン数（モデル別に 1,024〜4,096 の下限あり）でキャッシュ作成→即 `delete`。TTL は最小 | 下限トークンが大きく課金が読めない場合はスキップ |
| P6 | Google 検索グラウンディング | `tools:[{google_search:{}}]` 付きで1回。free 側の可否と課金メッセージ | — |
| P7 | (参考) `imagen-*` の `predict` | **既定では実施しない**。有料キーに実課金（1枚あたり数円）が発生するため。実施するならユーザー承認後・1枚上限 | 承認が無ければ実施しない |

各プローブで記録するもの: HTTP status / `error.status` / `quotaId` / `isFreeTierQuota` / レスポンス全文（キー除去後）/ 所要時間 / `usageMetadata`。

### 4.3 Phase 3 — 429 誘発による確定判定（フォールバック本命）

Phase 1/2 で決め手が無い場合の現実解。**issue #88 案A の実測版。**

- 対象モデル: `gemini-flash-lite-latest`（無料 15 RPM / 有料 Tier1 4,000 RPM と桁が違う＝分離が最大）
- 手順: 1トークン相当のプロンプト・`maxOutputTokens=1` を **N=20 リクエスト / 並列10** で発射し、最初の 429 までの経過時間と `quotaId` を記録
- 測るもの:
  - **時間**: free が 429 に到達するまでの秒数（＝キー登録時に待たせる時間）
  - **偽陽性**: paid キーが同条件で 429 を返さないこと（TPM 由来の 429 が出ないか）
  - **コスト**: paid 側 20 リクエストの課金額（見積: 1円未満のはず。実測で確認）
  - **副作用**: free 側の RPM 枠を1分間使い切ること（＝直後の一括判定が待たされる）
- **重要**: この方式は「一度 429 を踏むまで分からない」。したがって実装は**登録時の同期プローブではなく、一括判定中のランプアップ**に載せるのが本筋（§6 参照）。Phase 3 はその挙動の妥当性を数値で裏づけるために行う。

### 4.4 Phase 4 — RQ4 / RQ5（副次アウトカム）

- **RQ4（RPD）**: 上限を実際に使い切る実験は**しない**（無料 flash-lite で1,000件級＝70分以上かかり、割に合わない）。docs の値を一次ソースとして採り、実行中に RPD 系 quotaId を踏んだら文字列を記録する日和見方式にする。
- **RQ5（free プロファイル）**: 無料キーで concurrency 1 / delay を 13,000ms → 4,000ms（15 RPM）に上げ、100件を通して 429 発生率を測る。429 ゼロなら `BATCH_PROFILES.free` を更新。

## 5. 「自動判定を採用してよい」合格基準

以下を**すべて**満たすプローブのみ実装に採る。1つでも欠ければ自動判定は諦め、案B（手動選択＋安全側既定）にする。

1. **正確性**: 無料キー→free、有料キー→paid が **各3回×2時間帯 = 6/6 で一致**（時間帯を変えるのは他ユーザー負荷の影響を切り分けるため）
2. **コスト**: 有料キー1回あたりの課金が **1円未満**
3. **速度**: **10秒以内**（キー登録UIを固まらせない上限）
4. **副作用**: 無料キーの分あたり枠の消費が **1/3 以下**、RPD への影響が無視できる
5. **権限**: APIキーのみで完結（OAuth・GCPプロジェクト権限を要求しない）
6. **一過性障害に強い**: ネットワーク断や5xxを **free と誤判定しない**（判定不能は `unknown` を返し、既定=free に落とす。誤りを永続化しない）

## 6. 結果に応じた実装分岐

### どちらに転んでも先に入れる修正（実験結果に依存しない）

1. **PR #87 をマージする**（429適応スロットリングは全案の前提）
2. `#tier-select` に「無料」を追加し、**誤判定をユーザーが是正できる**ようにする
3. [batch.ts:70](../../src/sidepanel/features/llm/batch.ts#L70) の既定 `'tier1'` → **`'free'`**（判定不能時に安全側へ倒す）
4. [gemini-api.ts:566-574](../../src/lib/gemini-api.ts#L566-L574) のモデル数分岐を**削除**（F1 で無効と確定済み。残すと嘘を表示し続ける）
5. APIキーを URL クエリ（`?key=...`）から `x-goog-api-key` ヘッダへ移す。**現状はトレースバックやログにキーが載る経路がある**（AGENTS.md 9 / 過去に実事故あり）

### 分岐 →**ケースA で確定（2026-08-15）**

- **ケースA（Phase 1/2 で合格基準を満たすプローブが見つかった）** ← **これになった**
  → 自動判定を作り直す。判定結果は「初期値の提案」として扱い、手動選択で常に上書き可能にする。
  採用するプローブと実装方針は [report.md](report.md) の「推奨する実装」を参照。
- ~~ケースB（見つからない）~~ → 不要になった。ただし**実行時の安全網としての 429 適応スロットリング
  （PR #87）は引き続き必要**。判定器は公式APIではなく entitlement の副作用を観測する方式なので、
  Google 側の仕様変更で壊れる可能性がある（しかも「全キーを paid と誤判定する」危険な方向に壊れる）。
  - 重要: `isFreeTierQuota === true` は**減速の根拠にのみ使い、tier のロックには使わない**。
    有料 Tier 2/3 でも FreeTier バケットに落ちる既知事象があるため（[report.md](report.md) 参照）。

## 7. 実験の運用ルール（グローバル方針の適用）

`~/.claude/CLAUDE.md`「ネットワーク処理はバッチ化し、中断を前提に設計する」を適用する。本実験は最大でも数百リクエスト規模だが、以下は守る。

- **1試行ごとに JSONL 追記**（`results/probe_<phase>_<timestamp>.jsonl`）。メモリに溜めない
- **リトライはパースまで含める**。HTTP 200 でボディがエラー文書（`{"error":...}`）のケースを正常扱いしない
- **一過性の失敗を「free と判定」として永続化しない**。判定不能は `unknown` として記録する
- **キーをログに出さない**。`x-goog-api-key` ヘッダで送り、記録前に `redact()` を通す。リクエストURLはそのまま出力しない
- **進捗は試行数で数える**（ログ行数で報告しない）
- レート制限を守る（無料キー: 15 RPM を超えるのは Phase 3 の意図的な誘発時のみ）
